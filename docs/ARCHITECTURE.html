ThunderPermanent Serving Architecture

How we serve CMKL/MANGO1.5-Qwen3.5-9B on one A100-40GB to maximise on-time answers per joule. Every component runs on stock vLLM 0.32 through its official extension points (middleware, --scheduler-cls, quantized checkpoint, speculative config); there is no fork of vLLM.

1 · Request path (data plane)

One OpenAI-compatible endpoint on port 8000, one vLLM process, one GPU at a fixed 400 W power limit.

Client / grader

OpenAI API, streaming, tool calling, thinking on, temp 0, max_tokens up to 8192, prompts up to 32K

→

SLO middleware

ASGI slo_priority.py: thinking_token_budget = max_tokens − clamp(0.5·max_tokens, 24, 1024); metadata-only request log

→

vLLM 0.32 engine (stock, OpenAI server, qwen3 reasoning parser, qwen3_coder tool parser)

SLO scheduler

--scheduler-cls: EDF by TTFT deadline, late requests held at the back (never dropped), TPOT admission cap, pause doomed decodes while their avg TPOT < 45 ms

Chunked prefill

batch budget 2560 tok/step, long-prefill cap 600 (576 effective, 288-token blocks), prefix cache

INT8 W8A8 model

made from official BF16: per-channel RTN weights, dynamic per-token activations, CUTLASS INT8 GEMM

MTP speculative

model's own MTP head, K adapts to load (3/2/1), no MTP block drop for prefix cache

→

A100-SXM4-40GB

fixed 400 W for the whole run (rule: constant power)

metadata telemetry→ rebuild 300 items→ digital twin replay (±1 item vs grader)→ GPU sweep (~30 configs, flock)→ serve_final.sh→ Final submission↺

3 · General technique vs. tuned to this workload

general Transfers to other traffic

  • INT8 W8A8 for prefill-bound serving on Ampere (accuracy 91.8% vs 87.8% baseline)
  • SLO-aware scheduling: deadline order, late hold, TPOT-capped admission (goodput, not throughput)
  • Thinking budget so reasoning models always leave room to answer
  • Measure → replay → change one thing: the digital twin method

These took the score from 41.8 to 98.6.

tuned Specific to this trace

  • Exact values: batch 2560, long-prefill 600, MTP K thresholds 32/64, guard 45 ms
  • The last 1.4 points: same config scored 99.5 / 99.7 / 99.5 across runs; 300/300 is the new config plus run-to-run variance
  • For new traffic: re-run the twin on its own logs (about one hour of GPU time)

The twin uses only arrival times and token counts, never prompt text.

5 · Rules compliance

  • Derived weights made during the event from the official BF16 checkpoint; open-source tools only; no calibration data
  • Fixed 400 W power limit for every run; no dynamic power or clock changes
  • Grader generation settings untouched (thinking on, temperature 0, max_tokens); thinking budget approved by the organizers
  • No response caching; normal prefix KV cache only. Request logs hold metadata only (lengths, timings, finish reason)
  • One vLLM process on one GPU; no other GPU work during graded runs
